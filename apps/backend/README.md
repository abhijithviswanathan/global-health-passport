# Health Passport API — synthetic pilot implementation

Java 21, Spring Boot 3.5.16, PostgreSQL-compatible JDBC, Flyway migrations. The default database is persistent H2 at `data/passport`. Real clinical use is blocked by the release gates in the repository documentation.

## Run

Install JDK 21 and run `./mvnw test`, then `./mvnw package`. The wrapper downloads Maven 3.9.11 over HTTPS and verifies its SHA-512 checksum. Set `DEMO_MODE=true` and a private `DEMO_PASSWORD` of at least 12 characters before `./run.sh`. Accounts `patient`, `doctor`, `lab`, `pharmacy`, `admin`, `security` use that password only when the database is first initialized. If no password is supplied, a random password is written to owner-readable `data/demo-credentials.txt`. Do not publish that file. Later password changes must use identity workflows; changing the environment does not overwrite accounts.

The API binds to `127.0.0.1:8080`. Serve the web application through its same-origin API proxy. Set `COOKIE_SECURE=true` behind HTTPS. Production database configuration uses `DATABASE_URL=jdbc:postgresql://host:5432/passport`, `DATABASE_USER`, `DATABASE_PASSWORD`. PostgreSQL 17.11 passed all eight migrations and six inherited HTTP workflow tests; a separate logical application-data restore matched all rows, seven identity sequence states and the audit chain. See POSTGRES_VERIFICATION.md for the exact scope and recovery limitations.

## API conventions

GET `/api/csrf` initializes the session and returns `token`, `headerName`. Send `X-CSRF-TOKEN` and the session cookie on every POST, including login. POST `/api/auth/login` accepts username/password; GET `/api/me` returns the signed-in identity; POST `/api/auth/logout` invalidates the session. Unauthorized requests return 401; forbidden requests 403; invalid input 400; conflicting fills 409. Protected responses use `Cache-Control: no-store`.

User responses contain `id` (public UUID), `username`, `role`, `name`, `displayName`, `healthId`, `health_id`, `organization`. Internal numeric primary keys and password hashes are removed from responses. The patient Health ID is separately generated from 128 random bits; it is a lookup label, never an access credential.

GET `/api/users` lists synthetic doctor/lab/pharmacy recipient metadata. GET `/api/patients` returns the patient themselves or current consented patients for a clinical role. Admin receives no clinical list. Staff request access with POST `/api/access-requests` `{healthId,purpose:"treatment"}`; response does not reveal whether the Health ID exists. GET the same path lists own requests. Patient approval uses POST `/api/consents` `{patientId,granteeId,purpose:"treatment",expiresAt,scopes:[...]}`. Expiry is an ISO instant up to one year away. POST `/api/consents/{id}/revoke` revokes future access immediately within this single-process API. GET `/api/consents` lists the current user's grants.

GET `/api/patients/{id}/timeline` returns authorized records as an array. Every item includes `id,patient_id,kind,title,details,author_id,author_name,source,status,created_at,replaces_id,related_id` and structured order fields when present. Kind scopes are `allergy,condition,medication,encounter,lab_order,lab_result,prescription,dispense,note,imaging_report`. A laboratory sees only lab orders/results/imaging reports; a pharmacy sees only prescriptions/dispenses/allergies/medications even with broader consent. A timeline can be incomplete.

POST `/api/records` accepts `{patientId,kind,title,details,replacesId?,relatedId?}`. Patients may enter notes/allergies/conditions/medications, marked unverified. Doctors may write encounters, notes, allergies, conditions, medications, orders and prescriptions; labs results/reports; pharmacies dispensing events. Author-only amendments retain the old row and link the new version. Laboratory orders require `recipientId` of the assigned laboratory. Prescriptions require `recipientId` of the assigned pharmacy, integer `quantity`, optional `refills` (0–12), and `dosage,route,frequency,duration` strings. Laboratory results require `relatedId` for an active lab order assigned to the writer. Dispensing requires `relatedId` for an active prescription assigned to the writer, `quantity`, and `idempotencyKey`. One event consumes one fill, including partial quantities; total fills cannot exceed `1 + refills`. Repeating a key with the same prescription and quantity returns the original event; conflicting reuse is rejected. Maximum per-fill quantity is enforced. The API serializes these decisions and writes each event atomically; multi-instance operation requires database locking before release.

GET `/api/audit` lists the patient's/actor's own events, or up to 500 global events for the security role. The hash chain detects modifications relative to preserved events but is not external, immutable proof. GET `/api/patients/{id}/export` is an own-patient JSON export. GET `/api/patients/{id}/fhir` is an own-patient resource-specific R4 historical Bundle projection with provenance; GET `/api/fhir/metadata` describes this limited capability. No conformance certification, import, terminology binding or cross-region exchange is claimed. POST `/api/break-glass` is disabled and audited.

## Verification and limits

`WorkflowTest` drives real HTTP sessions through patient approval, doctor ordering, lab result, pharmacy dispensing, idempotency, refill exhaustion and revocation, and verifies CSRF rejection, role projection, administrator denial, export restrictions, expiry validation and amendment history. Identity-specific tests are maintained separately.

This backend is a single-process synthetic implementation. Independent penetration testing, production PostgreSQL operations, rate limiting across processes, independently anchored audit storage, encryption key operations, clinical coding/units, medically validated prescribing, external professional-license verification, actual malware-scanner operations, DICOM, partner FHIR validation, offline operation, production backups/restores and jurisdictional authorization are release blockers. Free-text medical information must remain synthetic. A session cookie is not a native mobile device credential. The client must explain any partially visible history.

## Passkeys and signed medication snapshots

Passkeys use Yubico `webauthn-server-core` verification with an exact origin allowlist, relying-party ID, mandatory user verification, credential ownership, and one-use session-bound challenges expiring after 180 seconds. Configure `WEBAUTHN_RP_ID` and `WEBAUTHN_ORIGINS`; local defaults require opening `http://localhost:5173` (the IP-address URL is a different WebAuthn relying party). POST `/api/passkeys/register/options` with `password` and enrolled `otp` to step up, then POST `/api/passkeys/register/finish` with `{requestId,credential}`. POST `/api/auth/passkey/options` with `username`, then `/api/auth/passkey/finish` with `{requestId,credential}`. Browser credential binary members must be encoded base64url. GET `/api/passkeys` returns own credential metadata; POST `/api/passkeys/{id}/revoke` requires password and any enrolled OTP. Recovery removes enrolled credentials and pending challenges. Password login for non-demo staff requires enrolled MFA by default (`REQUIRE_STAFF_MFA=true`); verified passkey login satisfies strong authentication. `production`/`prod` profiles reject demo mode and disabling staff MFA. These guards do not make deployment clinically approved.

POST `/api/medication-passports` with own `patientId` signs an active medication/prescription/allergy snapshot using Ed25519. The response includes a compact signed `credential`, its `records`, an opaque `reference`, and `qrPayload` containing only a short reference path. References expire in five minutes and GET `/api/medication-passports/ref/{reference}` requires authentication and authorization for every included record. GET `/api/medication-passports/public-key` exposes only the public JWK. POST `/api/medication-passports/verify` with `credential` checks local signature integrity and expiry. A valid signature does not certify medical accuracy, clinician authority, or dispensing permission.

Demo signing keys persist in owner-readable `data/medication-signing-keys.properties`. Non-demo mode requires `PASSPORT_SIGNING_PRIVATE_KEY` (base64 PKCS#8 Ed25519) and `PASSPORT_SIGNING_PUBLIC_KEY` (base64 X.509). Key rotation, issuer trust distribution, and revocation of already exported snapshots require production governance. Never package private keys with deliverables.

## Organization verification foundation

GET `/api/organization/members` returns only own-organization doctor/lab/pharmacy metadata to an administrator. POST `/api/organization/members/{id}/verification` accepts `{status:"verified"|"suspended",evidenceReference}`. The evidence value is a reference to an external onboarding decision, never a clinical record or a substitute for actual credential verification. Targets in other organizations, patients, administrators and security users cannot be changed. No account creation, role elevation, organization reassignment or administrator clinical access is exposed.

Every protected staff request checks current practitioner verification. Missing verification denies clinical staff access. Suspension transactionally revokes active sessions and consent grants addressed to the staff member; reinstatement does not resurrect either. New password/passkey logins are also denied while suspended. Seeded demonstration clinicians receive `synthetic_verified` only in explicit demo mode, labeled as synthetic fixtures. This status is not accepted outside demo mode. Actual staff onboarding and administrator organization membership remain externally provisioned release requirements. Organization labels currently form the administrative boundary and must be replaced by governed tenant identifiers before real multi-organization provisioning.

## Compact Health IDs

Canonical IDs now contain exactly nine letters/digits (excluding I/O/0/1). Existing long IDs remain lookup aliases after V9–V10. The latest default backend run passes 26 tests with 7 PostgreSQL cases skipped; the separate PostgreSQL run passes all 7 and validates V1–V10. See ADR0011 and the compact Health ID evidence in root docs.
